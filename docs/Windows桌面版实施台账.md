# Tensor Trail Windows 桌面版实施台账

本台账用于逐步执行目录整理、共享代码拆分和 Windows 桌面版开发。2026-11-09 已完成 M1（D0、D1、D2）：迁移基线、Git／目录整理与共享代码拆分。实际记录见 [目录整理验收](Windows目录整理验收.md) 和 [共享层拆分验收](Windows共享层拆分验收.md)。D3 桌面外壳和 D4 原生文件流程已完成，见 [桌面文件流程验收](Windows桌面文件流程验收.md)。D5 的 DPI、画布交互与大图测量也已完成，见 [桌面体验验收](Windows桌面体验验收.md)；M2 Windows 开发版验收完成。

**确定的方向：保留网页版，新增 Electron Windows 桌面版，共享 React 编辑器、TypeScript 模型核心和项目 JSON；Python 作为独立任务进程。** 首个交付目标为 Windows x64。Ubuntu 暂不开发，仅保留平台边界。

当前执行位置：**L00 与 29 项实施任务已完成，12 项未开始；下一项为 D6-01。**

## 1. 使用方式与状态

- 任务状态使用“未开始、进行中、待验收、已完成、阻塞、延期”。只有完成产出并取得验收证据，才标记“已完成”。
- 按依赖顺序执行；一次处理一个可验证任务或紧密关联的小批次。常规实施选择可依据本台账自行推进，遇到范围改变、文件冲突或无法满足的条件时再明确说明。
- 每次完成任务后更新任务状态及文末执行记录，填写实际文件、检查结果和提交号；没有提交时填写“未提交”。
- 目录迁移、行为重构和新功能分别形成可审查的变更，避免一次同时搬目录、改协议和改交互。
- Git 提交、推送及安装发布按当轮执行指令处理；写入台账本身不表示已执行这些操作。
- 既有网页版保持可运行。阶段验收未通过时，先修复或恢复该阶段，不继续叠加下一层改动。

## 2. 当前基线与目录问题

以下保留 2026-11-09 迁移前快照，供恢复和比较使用；当前 Git 已在根目录，网页入口为 `apps/web/`，详见执行记录。

| 项目 | 当前情况 |
| --- | --- |
| 开发目录 | 项目根目录，前端入口为 `app/` |
| Git 工作副本 | `.publish/tensor-trail/`；开发根目录目前没有 `.git` |
| Git 基线 | `8245aa2`，本地 `main` 与 `origin/main` 一致；副本工作区干净 |
| 未纳入该提交的本地工作 | Python CPU 环境说明、核心依赖清单、发布准备脚本调整，以及本台账等；迁移 Git 前必须逐项盘点 |
| 前端 | React 19、TypeScript 5.7、React Flow 12、Zustand 5、Vite 6；Node.js 20.15.1、npm 10.7.0 |
| 前端验证基线 | 46 个测试文件、851 项测试，以及 CLI 检查、TypeScript 和生产构建通过 |
| Python 环境 | `.conda/tensor-trail-cpu/`：Python 3.11.18、PyTorch 2.11.0+cpu、NumPy 1.26.4 |
| Python 验证基线 | 输入采集工具 7 项测试及 `pip check` 通过；尚无整个可视化图的通用 PyTorch 执行器 |
| 已有工作流 | 启动为空白工作区，手动打开 JSON 后关联文件，Ctrl+S 保存回该文件 |
| 用户工作资料 | `data/` 内有模型 JSON、Word 和 Visio 文件，不能当作程序源码整体发布 |

当前主要问题：

1. 开发目录和 Git 工作副本分开，依靠复制同步；多端开发与后续目录迁移容易只更新其中一处。
2. `app/src/` 同时放置网页入口、编辑器、模型核心和平台文件操作，没有独立的桌面入口。
3. `editor/fileActions.ts` 直接使用浏览器文件选择器；`ProjectFiles` 的句柄接口也带有浏览器文件写入流的形态。
4. `agent/model.ts` 导入 `editor/valueLinkEditing.ts` 的 `removeValueNodes`；后者又使用 `editor/clipboard.ts` 的纯图复制逻辑。拆共享包前必须理顺这条反向依赖，不能直接整目录搬走后靠路径别名掩盖问题。
5. `app/scripts/agent.mjs` 依赖 `../dist-agent/tensor-trail-agent.js`；目录调整必须同步处理 CLI、SDK 构建产物和示例路径。
6. 根 README、网页启动脚本、发布白名单和各文档均以 `app/` 为入口，需要随阶段更新。

## 3. 目标目录与职责

采用 **npm workspaces**，沿用现有 npm 工具链。根目录作为单一 Git 开发工作区；`.publish` 在迁移验证后保留为历史备份，不再作为第二处日常开发入口。

```text
neural-network-visualizer/
├─ package.json                  # workspaces 与统一命令
├─ package-lock.json             # 统一依赖锁文件
├─ apps/
│  ├─ web/                       # 浏览器入口、Vite、浏览器平台适配
│  └─ desktop/
│     ├─ src/main/               # Electron：窗口、菜单、文档会话、配置
│     ├─ src/preload/            # 向界面暴露限定的桌面接口
│     ├─ src/renderer/           # 薄入口，装配共享编辑器与桌面适配
│     └─ resources/             # Windows 图标与安装资源
├─ packages/
│  ├─ model-core/               # 图模型、算子、形状规则、校验、Agent API
│  ├─ editor-ui/                # React 编辑器、画布、节点、属性、编辑状态
│  ├─ platform-api/             # 两端共用的平台接口与消息类型
│  └─ cli/                      # Node 命令行入口与 CLI 检查
├─ python/                      # 现有输入采集工具；后续增加 worker 与协议
├─ examples/                    # 经检查可提交的 recipes、项目与输入快照示例
├─ tests/                       # 跨包集成与 Windows 桌面端到端验证
├─ docs/                        # 台账、架构、操作与验收记录
├─ scripts/                     # 统一开发、构建和检查入口
├─ release/                     # 桌面安装产物，忽略提交
├─ data/                        # 本地用户资料，保留原位并忽略提交
├─ references/                  # 本地参考源码，保留原位并忽略提交
├─ .conda/                      # 已建环境保留原位，忽略提交
└─ .publish/                    # 旧 Git 副本及备份，迁移后退出正常开发流程
```

`model-core` 初期将 `core/modules/agent` 放在同一个共享包中，保留其内部边界，避免拆出过多互相依赖的小包。它不依赖 React、Electron、浏览器 DOM 或编辑器状态。纯图编辑函数也归入该包。

`editor-ui` 不直接调用 Electron 或 Node 文件系统；通过 `platform-api` 获取文件、配置和可选 Python 任务能力。网页端与桌面端装配不同实现。桌面文件路径和 Python 解释器路径属于本机配置，不写入模型 JSON。

### 3.1 现有目录迁移表

| 当前位置 | 目标位置／处理方式 |
| --- | --- |
| `app/src/core/`、`modules/`、`agent/` | `packages/model-core/src/`；先抽离反向依赖 |

| `app/src/App.tsx`、`editor/`、`views/`、公共样式 | `packages/editor-ui/src/`；拆出浏览器平台代码 |
| `app/src/main.tsx`、`index.html`、`public/`、网页 Vite 配置 | `apps/web/` |
| `app/src/editor/fileActions.ts` | 浏览器实现放 `apps/web/`；共享会话逻辑和接口分别归入共享包 |
| `app/scripts/agent.mjs`、`test-cli.mjs`、Agent 构建配置 | `packages/cli/` 与共享核心的 SDK 构建；保留过渡入口 |
| `app/examples/` | 根 `examples/`，同步修正所有 CLI 和文档路径 |
| `app/tests/` | 单元测试随对应包迁移；跨包与桌面测试放根 `tests/`，保留逐项映射 |
| `python/`、`.conda/` | 保持原位；不搬动现有 Conda 环境 |
| 当前本地根 README | 先保留副本于 `docs/local/` 等被忽略位置；根 README 改为统一仓库入口 |
| `docs/GitHub-README.md` | Git 根目录统一后合并入口，停止长期维护两份含义重复的首页 |
| `app/start.cmd` | 迁移期间保留兼容启动入口；最终由根命令调用网页／桌面入口 |
| `node_modules/`、缓存、`dist/`、`dist-agent/` | 不搬运依赖和旧产物；根据新的统一锁文件重新安装、构建 |

不移动 `data/` 的用户原件，不重命名 `.conda` 环境目录，不直接删除 `.publish` 或参考源码。

## 6. 统一验收与回退规则

### 6.1 每个阶段至少记录

1. 网页和相关 CLI 是否仍能启动、构建。
2. 受影响测试、构建和实际操作的命令与结果。
3. 旧项目 JSON 是否仍能打开、修改后再次打开。
4. 阶段改动是否进入单一源码位置，是否残留对旧 `app/`／`.publish` 的生产依赖。
5. 已知问题、未验证内容和下一任务 ID。

仅文件移动或文档修改不机械重复全部测试；共享规则、会话或保存语义变化时，运行相关回归。Windows 安装和实际交互结果必须来自真实运行，不能用打包命令退出成功代替。

### 6.2 分阶段回退点

| 范围 | 回退方法 |
| --- | --- |
| Git 与目录整理 | 保留原副本和未提交文件清单，在迁移检查点恢复文件与入口；不覆盖 `data/` 或环境目录 |
| 共享包拆分 | 返回上一个网页／CLI 均可构建的检查点，恢复导出与路径；保留未完成改动的独立副本 |
| Electron 与文件服务 | 网页入口可继续运行；保留用户编辑及源 JSON，不用有问题的保存逻辑重写文件 |
| 安装包 | 回到上一个验证过的应用版本；用户项目、配置与应用安装文件分别处理 |
| Python 集成 | 停用桌面运行时能力，保留图编辑与现有 Python CLI；不修改其他 Conda 环境 |

### 6.3 Ubuntu 边界，暂缓执行

共享包不写死 Windows 路径、注册表或安装目录。平台服务、Python 启动和安装资源放入对应实现。将来在 Ubuntu 环境单独处理文件对话框、权限、Python 环境和 Linux 打包；不把 Windows Conda 目录或 `.exe` 当成可跨系统复用的运行时。
